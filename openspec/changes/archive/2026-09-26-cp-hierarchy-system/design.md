## Context

The CP (Channel Partner) surface already exists in two halves that must stay in sync:

- **Admin side** (`app/(admin)/admin/freelancer-cp/*`) — four pages (`page.js` overview, `head-cp`, `company`, `digital`, `field`) all rendering the same generic `components/admin/freelancer-cp/CPTypeWorkspace.jsx`, parameterized by `cpType` / `leadCpTypes`. Data lives in `localStorage` collections defined in `lib/adminStorage.js` (`ADMIN_KEYS.cpNetwork`, `cpLeads`, `campaignVideos`, `commissions`, `invitationCodes`), read/written through `adminAxios` calls to `/api/admin/*` mock routes.
- **Public portal side** (`app/portal/freelancer/page.js` → `components/portal/freelancer/FreelancerPortalClient.jsx`) — one shared dashboard for all three freelancer `cpType`s (`company`/`digital`/`field`), driven by demo data in `lib/demoPortal.js` (`CP_LEADS`, `CP_NETWORK`, `CP_STATS`, etc.) or the real logged-in user's `cpType`.

Today, lead visibility is filter-based, not routing-based: `CPTypeWorkspace` computes `effectiveLeadCpTypes = leadCpTypes || [cpType]` and shows any lead whose `submittedBy.cpType` is in that list. This means Digital/Field leads are already visible in the Head CP view (`leadCpTypes: ["digital", "field"]`) purely as a side effect of the filter, with no actual "forwarding" action, and Company CP only ever sees leads it submitted itself — never leads from Digital/Field CPs. There is no property/project assignment model at all: `/admin/properties` has Add/Edit/Delete/View/Featured actions but nothing that connects a property to a CP.

Separately, `app/api/properties`, `app/api/leads`, `app/api/users` show this project has moved from pure-mock to a real API + MongoDB backend (`lib/mongodb.js`, `lib/propertiesServer.js`) for properties/users/leads, while the CP-specific collections (`cpNetwork`, `cpLeads`, `campaignVideos`, `commissions`, `invitationCodes`) are still `localStorage`-only. This design keeps CP data on the existing `localStorage`-via-`adminAxios` pattern (consistent with the rest of `CPTypeWorkspace`) rather than introducing a new backend model, to avoid a disproportionate migration inside a UI/workflow change.

## Goals / Non-Goals

**Goals:**
- Replace the incidental `submittedBy.cpType` lead filter with an explicit `routingStage` field that drives visibility, so every lead is owned by exactly one stage at a time: `head-cp → company-cp → field-cp | digital-cp`.
- Introduce a `cpAssignments` collection so Head CP can hand a *property/project* (not just a lead) down to a Company CP, and Company CP can delegate it onward to a specific Field or Digital CP.
- Give Field CP and Digital CP each a distinct, purpose-built set of actions once work reaches them (site-visit pipeline vs. campaign/creative pipeline) instead of the identical generic table both currently get.
- Keep the admin (`CPTypeWorkspace`) and public portal (`FreelancerPortalClient`) views showing the same underlying state, since both already read the same `localStorage` collections.

**Non-Goals:**
- No new authentication/authorization system. "Head CP" continues to mean "whoever is logged into `/admin`" — there is one Head CP, matching the stated plan (point 1: "super admin/admin"). Multi-seat admin roles are out of scope.
- No migration of `cpNetwork`/`cpLeads`/`cpAssignments` to MongoDB in this change — they stay on the existing `localStorage` + `adminAxios` mock pattern used by the rest of the CP workspace, to keep the change scoped to workflow/UI.
- No real ad-network or SMS/webhook integration for "leads generated by an ad" — Digital CP leads continue to be created the same way they are today (manually logged / demo-seeded), just tagged with the new `routingStage`.
- No changes to commission calculation logic — only which stage/CP a lead or project is currently sitting with.

## Decisions

**1. `routingStage` replaces `leadCpTypes`-based filtering as the source of truth for lead visibility.**
Every lead gains `routingStage: "head-cp" | "company-cp" | "field-cp" | "digital-cp"` and keeps `submittedBy.cpType` purely as provenance (who/what originated it), no longer as the visibility key. `CPTypeWorkspace` filters leads by `routingStage === stageForThisPage` instead of `effectiveLeadCpTypes.includes(submittedBy?.cpType)`.
*Alternative considered*: keep the existing "leadCpTypes bypass" filter and just add a forward action on top. Rejected — it would leave Digital/Field leads visible in two places at once (their own page AND Head CP) with no single owner, which is exactly the ambiguity the proposal is meant to remove.

**2. New `cpAssignments` collection, separate from `cpLeads`.**
A `cpAssignment` record represents a *property/project* handed down the chain: `{ id, propertyId, propertyTitle, level: "head-to-company" | "company-to-field" | "company-to-digital", assignedByCpType, assignedByName, assignedToCpType, assignedToName, parentAssignmentId, status: "Assigned" | "In Progress" | "Completed", createdAt }`.
*Alternative considered*: overload `cpLeads` with a "project-type" record. Rejected — leads and project assignments have different lifecycles (a lead is a prospect; an assignment is a work item over a property) and conflating them would make both the Leads tab and KPI counts harder to reason about.

**3. Head CP inbox action is "Forward to Company CP" (single hop), Company CP action is "Delegate to Field/Digital CP" (single hop).**
No multi-hop generic router — each stage has exactly one explicit forward action to the next stage down, matching points 7-8 literally ("sabse phele HEAD CP ko show", "forward to company cp"). Company CP's existing `assignedTo` select in `LEAD_COLUMNS` (currently hardcoded to Field CP names only) is extended to a two-part chooser: CP type (Field/Digital) then partner name.
*Alternative considered*: let Head CP forward directly to Field/Digital, skipping Company CP. Rejected — explicitly contradicts point 4 ("company cp is the head of digital and field cp"); Company CP must be the only path to Field/Digital.

**4. Field CP and Digital CP get dedicated tabs, not a shared generic one.**
`CPTypeWorkspace` gains two new optional tabs, enabled per page: `siteVisits` (Field CP — schedule/log visits against an assigned project, backed by a new `cpSiteVisits` collection keyed by `assignmentId`) and reuses the existing `campaignVideos` tab (Digital CP — already exists, just needs to be scoped to *assigned* projects instead of all projects). This keeps the generic-workspace pattern already established by the four `page.js` files (each just flips props) rather than forking into four bespoke components.
*Alternative considered*: build fully separate `FieldCPWorkspace` / `DigitalCPWorkspace` components. Rejected — the existing four-pages-one-component pattern works well and this change fits inside it via a couple of new optional props/tabs.

**5. "Assign to Company CP" lives on the existing Properties admin table, not a new page.**
`/admin/properties` already has the canonical property list with row actions; adding one more action (`Assign to Company CP`, opening a small picker dialog) is the smallest change that satisfies point 2/3, and keeps property CRUD and property-assignment in one place Head CP already visits.

## Risks / Trade-offs

- **[Risk] Existing demo/seed data (`lib/demoPortal.js` `CP_LEADS`, any seeded `cpLeads` in `lib/adminStorage.js`) has no `routingStage`, so after this change those leads would vanish from every view (filtered out everywhere).** → Mitigation: migration step backfills `routingStage: "head-cp"` on all existing demo/seed leads as part of the same change (see tasks), and a defensive default (`lead.routingStage || "head-cp"`) in the filter so any lead missing the field still surfaces somewhere instead of disappearing silently.
- **[Risk] Two-hop delegation (Head→Company→Field/Digital) adds friction versus today's instant visibility — a real Head CP might forget to forward a lead, stalling the pipeline.** → Mitigation: Head CP inbox shows a prominent unforwarded-count KPI (already has a KPI-card row pattern in `CPTypeWorkspace`) so pending forwards are visible, not silent.
- **[Risk] `localStorage`-backed collections don't sync across devices/browsers — Head CP and Company CP acting from different machines won't see each other's writes in real time.** → Accepted trade-off, consistent with the rest of the CP feature today (same limitation already exists for `cpNetwork`/`cpLeads`); out of scope to fix here per Non-Goals.
- **[Risk] Extending `LEAD_COLUMNS`'s assign-select to two CP types (Field/Digital) inside `CPTypeWorkspace` adds conditional complexity to an already-shared component.** → Mitigation: keep the two-step chooser (type, then name) as a single small subcomponent so the generic table column stays simple.

## Migration Plan

1. Add `routingStage` (default `"head-cp"`) to the lead shape in `lib/adminStorage.js` and `lib/demoPortal.js`; backfill existing seeded/demo lead records.
2. Add `ADMIN_KEYS.cpAssignments` and `ADMIN_KEYS.cpSiteVisits` collections (empty arrays by default — no backfill needed, these are new concepts).
3. Ship `CPTypeWorkspace` changes behind the existing per-page prop flags (`showSiteVisits`, `showAssignedProjects`) so `head-cp`/`company`/`digital`/`field` pages opt in individually — no big-bang cutover risk since each page's props change independently.
4. Update the Properties admin table and `FreelancerPortalClient` in the same change (both read the same underlying collections, so they must ship together to avoid one surface showing stale/inconsistent state).
5. No rollback complexity beyond reverting the code — no destructive data changes, `routingStage` is additive to existing lead objects.

## Open Questions

- Should a Company CP be allowed to delegate the *same* project to both a Field CP and a Digital CP simultaneously (parallel work), or is it strictly either/or per project? Proposal text ("decide karega ki isko filed cp ko dena hai ya digital cp ko") reads as either/or — design assumes **either/or per assignment**, but a project could get two separate `cpAssignment` records (one per CP type) if the business wants both running at once. Defaulting to allowing multiple assignment records per property so this isn't blocked, but the UI in v1 will only support one active delegation per CP type per property.
- Does Field CP site-visit logging need photo upload (there's an existing `lib/uploadToR2.js` / `lib/mediaCompress.js` pipeline used elsewhere)? Defaulting to **notes-only** for v1 to keep scope tight; photo attachments can reuse the existing upload pipeline in a follow-up.
